# 第二步：限制 Git 只上传前后端

日期：2026-10-15。

## 本次规则与原因

远端仓库只保留根目录下的 `frontend/`、`backend/` 两个文件夹。设计稿、需求文档、根目录学习文档和辅助文件继续保存在本地。

本次检查发现本地首次提交包含 7,076 个文件，其中 6,907 个位于范围外。通过 GitHub 仓库信息和分支列表确认，远端当时为空。因此处理的是未推送的本地首次提交，不需要改写远端历史，也不需要强制推送。

Git 是记录文件版本的工具。暂存区是“准备放进下一次提交的文件快照”；提交把这个快照保存为一个版本；推送把本地提交传到远端仓库。这三个动作发生在不同阶段，所以只修改忽略规则不能自动纠正已经保存的提交。

## 实现步骤

1. **限制候选文件。** 根目录 `.gitignore` 默认忽略所有项目，只放行两个目录。此文件自身也仅保留本地。两个目录内部各有可随代码分发的 `.gitignore`，继续排除依赖、构建产物、虚拟环境、缓存和实际环境配置，保留 `.env.example` 配置示例。
2. **备份原始提交。** 原提交保存到本机 `output/git-scope/before-cleanup.bundle`。bundle 是 Git 的离线备份文件；它保存旧版本，方便必要时恢复核对，不会被本次白名单上传。
3. **移除额外跟踪。** `git rm --cached` 只把文件移出暂存记录，保留工作目录中的实际文件。这里不使用会删除本地文件的清理命令。
4. **修正未推送提交。** 只有在确认远端为空、本地只有一个首次提交时，才使用 `git commit --amend --no-edit` 重新保存这个首次版本。amend 表示修正最近一次提交；它会改变提交编号，但保留原提交说明。不能把这个方式直接套到别人已经使用的共享历史。
5. **安装自动检查。** 钩子是 Git 在特定动作前自动调用的检查程序。`pre-commit` 检查完整暂存快照，`pre-push` 检查本次即将上传的新提交；发现目录外文件就停止操作。检查不会删除本地文件，也不修改运行中的应用。
6. **验证后交由用户推送。** 按用户最新要求停止自动上传，只准备本地提交和忽略规则。用户手动执行普通推送；普通推送会在远端出现不兼容的新提交时拒绝覆盖，本步骤不使用强制推送。

## 当前状态与手动上传

停止自动上传之前，远端已经创建了一个只包含 `backend/.gitignore` 的初始化提交，完整项目尚未发布到远端分支。部分字体文件已传送为尚未关联到提交的 Git 对象；对象是 Git 内部保存文件内容的形式，这些内容已经离开本机，但不在当前分支的文件列表中。它们都属于允许的 `frontend/` 范围，没有向远端分支提交目录外资料。

为了让后续手动推送能正常进行，本地先读取这个远端初始化提交，并将项目快照接在它后面。读取远端称为 `fetch`，只下载已有记录；本地提交记录的整理不会上传代码。整理前另存本地备份 `output/git-scope/before-manual-alignment.bundle`，保留原文件和已检查的项目快照。

在 PowerShell 中进入项目根目录，确认本地检查通过后由你上传：

```powershell
cd E:\项目\fixFlow
python backend/scripts/check_git_scope.py --index
git ls-tree --name-only HEAD
git push -u origin main
```

当前项目已准备好本地提交，因此无需再次提交同一批内容。`origin` 是此仓库远端地址的名称，`main` 是分支名称，分支用于指向一条开发记录；`-u` 保存本地与远端分支的对应关系，之后可直接执行 `git push`。若命令提示登录，使用你自己的 GitHub 账号完成 Git 命令行认证；连接应用的授权不会自动成为命令行的登录凭据。不要添加强制推送参数。

以后有代码修改时，先添加两个目录内的变更，再提交和推送：

```powershell
git add -- frontend backend
git status --short
git commit -m "说明本次修改"
git push
```

根目录的 `.gitignore` 自身也被忽略，以满足远端只能出现两个目录的要求；本机规则已经生效。`.gitignore` 控制正常添加文件时的忽略行为，不能自动清理已有提交，也可以被强制添加绕过；本次保留了已经配置的本地钩子继续核验范围。

## 在其他电脑启用检查

新克隆的仓库要在根目录安装一次本地检查：

```powershell
git config --local core.hooksPath backend/.githooks
```

`--local` 表示只修改当前仓库的设置，不影响电脑上的其他项目。这个配置不会随着克隆自动生效。钩子需要电脑已有 Python；前一步安装的 Python 可以直接运行检查脚本，无需新增第三方依赖。

新克隆的仓库默认只有前后端。如果以后又在根目录放入个人资料，也可在本机创建根 `.gitignore`：

```gitignore
/*
!/frontend/
!/backend/
```

手动检查暂存区及当前提交：

```powershell
python backend/scripts/check_git_scope.py --index
python backend/scripts/check_git_scope.py --tree (git rev-parse HEAD)
git ls-tree --name-only HEAD
```

最后一条命令应只输出 `backend`、`frontend`。这套规则是本地防误操作检查，不是 GitHub 服务端权限设置；其他克隆需要安装钩子，远端网页操作也不由本机钩子控制。

## 验证与面试要求

测试使用独立临时仓库，不会向测试仓库推送任何数据，覆盖：正常前后端变更、强制暂存范围外文件、保留本地文件的纠正提交、首次推送历史检查，以及缺少远端父提交时停止检查。

本步骤的面试要求是能解释“忽略、取消跟踪、提交、推送”的区别，并能证明限制真的生效。最终检查还要确认本地资料保留、两个目录内的正常开发不受影响、其他项目的 Git 设置没有改变。

## 面试题与答案

### 1. 为什么新增忽略规则后，旧文件仍可能被上传？

**总结版本：** 忽略规则主要控制未跟踪文件，已经进入 Git 的文件需要先取消跟踪。

**详细版本：** 假设设计稿已经出现在上一次提交中，Git 已经认识这个文件。后来在 `.gitignore` 写上设计稿的名字，Git 不会自动把旧提交中的记录删除。因此要把它从准备提交的快照里移除，并保存一个纠正后的版本。实际文件可以继续留在电脑上。

### 2. `git rm --cached` 会删掉电脑上的文件吗？

**总结版本：** 不会，它取消暂存记录中的文件跟踪，本地文件保留。

**详细版本：** `git rm` 默认会同时影响暂存记录与工作目录；加上 `--cached` 后只处理暂存记录。提交后，新的版本里不再包含这些文件，但电脑上仍然可以打开设计稿和文档。因此“远端不再跟踪”和“电脑上删除文件”是不同操作。

### 3. 为什么本次可以修正首次提交？

**总结版本：** 本次确认远端为空，首次提交尚未共享，修正它不会覆盖远端已经存在的版本。

**详细版本：** 修正提交会产生新的提交编号。如果旧编号已经被别人使用，直接替换会使双方历史不一致。本次只有一个本地首次提交，远端分支为空，所以先备份再修正即可。如果以后发现已经推送的版本包含多余文件，通常增加普通纠正提交；若要求从全部历史彻底移除资料，则需要另行确认历史清理范围和协作影响。

### 4. 忽略规则和钩子为什么都需要？

**总结版本：** 忽略规则减少误选，钩子检查最终提交与推送内容，两者覆盖不同阶段。

**详细版本：** 平时执行添加文件时，忽略规则会跳过根目录个人资料。但用户仍可能强制添加文件，或者旧文件已经被跟踪。提交钩子直接检查完整暂存快照，就能发现这些情况。推送钩子继续核验新提交历史，防止最终目录虽然干净、待上传的祖先提交却仍带有范围外文件。

### 5. 检查为什么不能只看删除文件清单？

**总结版本：** 纠正提交需要删除范围外记录，应检查删除完成后的快照是否合法。

**详细版本：** 本次取消跟踪设计稿后，变更清单里会出现设计稿的删除记录。如果把“出现范围外路径”一律当成错误，这次清理本身也会被拦截。因此提交检查读取整个暂存区，只判断下一次提交实际保留哪些文件；删除范围外记录是符合目标的操作。
